## Frontend public contract

The View receives:

```js
{
  decisionContext,
  evaluation,
  setEvaluation,
  collectiveEvaluation,
  readOnly,
}
```

There is intentionally no `loading` prop.

Loading, save, submit and dialog lifecycle are owned by the host.

The View is not mounted while the evaluation payload is unavailable.

### `decisionContext`

Contains the issue/model/problem information already resolved by CreteValleyDSS.

Use this data instead of fetching application state again.

### `evaluation`

The complete current evaluation payload owned by this structure.

The View should render from this value.

Do not mutate it in place.

### `setEvaluation(nextEvaluation)`

Replaces the complete current evaluation payload.

It is not a cell setter and not a patch API.

Build the complete next payload and call:

```js
setEvaluation(nextEvaluation);
```

### `collectiveEvaluation`

Contains the collective evaluation payload when the host makes it visible.

It may be `null`.

Treat it as read-only presentation data.

Do not write collective values into the expert's `evaluation` unless the structure explicitly requires that behavior.

### `readOnly`

When `true`, the View must not allow evaluation edits.

Any interactive input that changes `evaluation` must be disabled or otherwise non-editable.

## Expression Domain inputs

CreteValleyDSS already owns the UI and validation rules for criterion Expression Domain values.

If this Evaluation Structure asks the expert to enter a value belonging to:

```js
criterion.expressionDomain
```

do not create a custom domain-specific input.

Reuse:

```js
ExpressionDomainEvaluationInput
```

from the public Expression Domains feature.

From a View at this package root, the public import is:

```js
import {
  ExpressionDomainEvaluationInput,
  validateExpressionDomainEvaluation,
} from "../../../../expressionDomains";
```

A typical input looks like:

```jsx
<ExpressionDomainEvaluationInput
  expressionDomain={criterion.expressionDomain}
  value={value}
  onChange={(nextValue) => {
    // Build the complete next evaluation payload.
    // Then call setEvaluation(nextEvaluation).
  }}
  disabled={readOnly}
  error={Boolean(error)}
  showHelperText={false}
/>
```

The Expression Domain layer selects the correct input using `expressionDomain.typeKey`.

Do not recreate:

- numeric continuous inputs;
- numeric discrete inputs;
- linguistic ordinal selectors;
- linguistic fuzzy selectors;
- linguistic 2-tuple selectors;
- domain-specific parsing or validation.

Frontend domain validation is available through:

```js
validateExpressionDomainEvaluation({
  value,
  expressionDomain,
});
```

For example:

```js
const validateValue = ({ value, expressionDomain }) => {
  if (value === "") {
    return "";
  }

  try {
    validateExpressionDomainEvaluation({
      value,
      expressionDomain,
    });
    return "";
  } catch (error) {
    return error instanceof Error ? error.message : "Value is invalid.";
  }
};
```

The Evaluation Structure still owns validation and organization of its surrounding payload shape.

## Updating the evaluation

Treat `evaluation` as immutable input.

A structure-specific operation may build the next payload, for example:

```js
const nextEvaluation = {
  ...evaluation,
  // structure-specific changes
};

setEvaluation(nextEvaluation);
```

For nested structures, clone every object/array that changes.

Do not rely on in-place mutation followed by `setEvaluation(evaluation)`.

## File organization

Keep the implementation as small as practical.

The generated scaffold is intentionally minimal.

If additional files are genuinely useful, follow current Decision Plugin conventions:

```text
components/
operations/
styles/
```

Use them as follows:

- `components/` — structure-specific React subcomponents;
- `operations/` — pure structure-specific transformations, validation, formatting or payload operations;
- `styles/` — extracted MUI `sx`/style definitions.

Style filenames should normally follow:

```text
<ComponentName>.styles.js
```

Operation filenames should describe the operation directly, for example:

```text
updateValue.js
validateValue.js
buildRows.js
resolveCollective.js
```

Do not create folders or helper files only to satisfy this convention.

Do not create generic `utils/`, `helpers/`, `services/` or hooks without a concrete need.
