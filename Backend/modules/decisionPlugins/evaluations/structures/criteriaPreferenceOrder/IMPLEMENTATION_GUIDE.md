## Persistence model

Evaluation payloads are intentionally stored in MongoDB using Mongoose `Schema.Types.Mixed`.

There is no universal database shape shared by all Evaluation Structures.

This is deliberate: each Evaluation Structure owns its canonical payload shape.

Therefore:

- do not modify the shared evaluation database schema to support this structure;
- define the payload shape required by this structure;
- validate and normalize that shape at the plugin boundary;
- do not treat `Mixed` as absence of validation;
- do not add structure-specific fields to shared application models.

  payload,

`payload` is the currently stored payload, or `null` when no evaluation has been stored yet.

`decisionContext` contains the issue data already resolved by CreteValleyDSS.

Return the complete payload that the Frontend View should receive.

If the canonical stored payload is already suitable for the Frontend, prefer returning it directly instead of introducing unnecessary transformations.

### `saveCriteriaPreferenceOrderPayload`

```js
async ({
  payload,
  decisionContext,
  mode,
}) => storedPayload
```

`mode` is:

- `"draft"` — incomplete data may be accepted when appropriate;
- `"submit"` — the definitive payload must satisfy every rule required for submission.

Return the complete canonical payload that must be persisted.

Do not mutate the received payload.

## Expression-domain evaluations

The canonical expected domain comes from:

```js

```

```js

  value,
  expressionDomain,

```

Do not duplicate numeric range validation, linguistic-label validation, linguistic 2-tuple validation, fuzzy validation or other domain-specific rules inside this structure.

Do not trust an Expression Domain supplied inside the evaluation payload when the canonical criterion domain is already available from `decisionContext`.

Structure-specific validation is still the Evaluation Structure's responsibility: payload shape, required rows/cells, alternative IDs, criterion IDs, draft/submit rules, and similar rules.
